# 02 · 提示词手册

> 版本 v1.0 ／ 2026-10-27 ／ 本文件是**提示词的唯一权威源**。`03` 里只写 `用 T05`，正文在这里。

---

## 一、使用须知

### 1.1 先分清两类提示词（**最容易混的地方**）

| | 在哪 | 给谁看 | 作用 |
|---|---|---|---|
| **产品运行时提示词** | `llm/prompts.py` 的 `SYSTEM_PROMPT` | 程序运行时调用的大模型 | 把用户的自然语言解析成 `PlanRequest` JSON |
| **编程助手提示词**（本文件） | 你复制粘贴到 LearnBuddy 对话里 | 帮你写代码的 AI | 让它读懂这个项目、只改该改的地方 |

**两者不能互换。** 改 `llm/prompts.py` 不会让 AI 更懂你的项目；本文件的卡片也不会影响程序运行。

### 1.2 一条好提示词的五个槽位

| 槽位 | 回答什么 | 缺了会怎样 |
|---|---|---|
| **目标** | 这次要达成什么（一句话，可验收） | AI 自由发挥，做多了或做偏了 |
| **上下文** | 相关文件、报错原文、复现命令 | AI 靠猜，猜错就改错地方 |
| **约束** | 只允许改哪些文件、不许做什么 | 顺手重构、顺手改冻结文件 |
| **输出格式** | 要它交什么（补丁？命令？三段式说明？） | 交一大段散文，你得自己找重点 |
| **自检** | 让它先自查再交付 | 交来就跑不通 |

### 1.3 上下文投喂清单

| 该贴 | 为什么 | 怎么贴 |
|---|---|---|
| 要改的文件**全文** | AI 才能看到 `_fill_day` 这种内部函数 | 直接贴代码块 |
| 相关**测试文件** | 让它知道不能破坏什么 | 贴 `tests/test_engine.py` |
| **报错原文完整 traceback** | 只贴最后一行等于让 AI 猜 | 整段复制 |
| **复现命令 + 真实输出** | 我要它复现同一个现象 | 代码块 |
| `PlanRequest` 的**字段名列表** | 不用贴全文，贴签名就够 | 见 1.4 |
| ❌ 整个仓库 | 噪声太大，AI 反而乱改 | — |
| ❌ `.venv`、`.idea`、`.env` | 无关且体积大 | — |

### 1.4 固定上下文包（每次开场贴这一段，省事又稳）

```text
【项目】D:\projects\ai-trip-planner（Python 3.14.6 + Streamlit 1.66.1，无 pytest，用标准库 unittest）
【分层】ui/ → engine/ → data/ → csv，禁止反向 import；engine/models.py 与 schemas/ 已冻结
【契约】PlanRequest(city, days, start_time, end_time, daily_budget, interests, avoid,
        pace, start_poi_id, top_n, raw_query)
        PlanResponse(request, days, warnings, metrics, strategy, scenario, generated_at)
        DayPlan(day_index, items, total_cost, total_stay_min, total_travel_min, total_distance_km)
        ItineraryItem(seq, poi_id, name, lat, lon, arrive, leave, stay_min, cost, transport, reason)
【业务外置】预算/时间窗/权重/节奏系数只能写在 config/scenarios/*.toml；POI 只能写在 data/*.csv
【验证】.venv\Scripts\python.exe -m unittest discover -s tests -t .
```

### 1.5 三条安全红线（每条提示词都要带上）

1. **不许改** `engine/models.py`、`schemas/itinerary.schema.json`、`docs/接口契约.md`
2. **不许装** 新依赖（不引入 pytest / pandas 之外的东西）
3. **不许整文件重写** —— 只给 diff 或带行号的局部替换

## 二、两条通用骨架（最先复制）

### T00 · 开场模板

**用在哪一步**：每次**新开对话**的第一条消息（配合 `05` 的 D1–D6 判定）。
**必带上下文**：1.4 的固定上下文包 + 当前分支名 + 这次只做一件事。

```text
你是我的 Python 项目协作助手。先只读、不要改任何文件。

【项目】<粘贴 1.4 固定上下文包>

【当前分支】fix/dead-links（用 git branch --show-current 确认为准）
【上一次进展】<一句话，例如：已完成 9 处缺陷修复并合并到 main>
【这次只做一件事】<例如：给 strategies.py 加一个贪心算法 greedy>
【完成标准】<例如：--strategy greedy 能跑；43 个测试仍全绿；eval 里 greedy 总分高于 random>

先做三件事，等我确认后再动手：
1. 用 5 行复述你对任务的理解
2. 列出你打算改哪些文件（只列路径）
3. 指出你认为可能被我漏掉的风险
```

**期望输出**：三段，不改代码。
**反模式**：一上来就说"帮我优化这个项目" —— AI 会同时改 5 个文件。

### T15 · 收尾模板

**用在哪一步**：AI 说"改好了"之后。

```text
交付前请自查并逐条回答：
1. 你改了哪些文件？每个文件几行？用 git diff --stat 的格式给我
2. 有没有碰 engine/models.py / schemas/ / docs/接口契约.md？（必须是"没有"）
3. 有没有新增依赖？（必须是"没有"）
4. 有没有任何地方出现具体金额、具体标签、具体时间这类业务数值？（必须挪进 TOML/CSV）
5. 我该跑哪几条命令验证？给出可直接复制的完整命令（含 .venv\Scripts\python.exe 前缀）
6. 会不会让现有 43 个测试变红？如果会，是哪几个、为什么
最后给我一条 Conventional Commits 格式的 commit message（中文正文）。
```

**期望输出**：六问六答 + 一条 commit message。
**反模式**：只问"改好了吗" —— 它会回"是的，已全部完成"，而实际没跑过。

## 三、任务卡 T01–T14

> 格式说明：每张卡固定五段。**"反模式"比"正文"更值得读**——它告诉你什么写法会让 AI 跑偏。

### T01 · 先读懂再动手（只读）

**用在哪**：接手陌生文件、或 AI 改错地方之后。
**必带**：目标文件全文 + 你的一段疑问。
```text
只读，不要改文件。读 <文件路径>，输出：
1. 这个文件的职责，一句话
2. 它对外暴露的函数/类清单，每个一句话
3. 它依赖谁、被谁依赖（看 import）
4. 你认为最容易被改错的 3 个地方，以及为什么
```
**期望**：结构图 + 3 个风险点。
**反模式**：让它"总结一下这个项目"——范围太大，输出全是正确的废话。

### T02 · 换真实场景数据

**用在哪**：`03` 分支 2 `feat/data-real`。
**必带**：`data/README.md` 全文 + `config/scenarios/template.toml` + 你的真实 POI 清单（哪怕只有 10 条）。
```text
我要把占位数据换成真实数据，代码一行都不许改。
1. 按 data/README.md 的列口径，把我下面这份清单整理成 pois.csv（utf-8-sig）
2. 复制 template.toml 生成 campus.toml，填 day_start/day_end/daily_budget/max_poi_per_day
3. 填 [interest_alias]：左边是用户会说的词，右边必须是我 CSV 里 tags 出现过的值
4. 列一个自检清单：列名、时间格式、tags 用竖线、ID 唯一、坐标范围
我的数据：<粘贴>
```
**期望**：两个文件 + 自检清单。
**反模式**：让 AI "顺便改改 engine 让它适配新数据" —— 数据层是外置的，代码不该动。

### T03 · 新增一个算法

**用在哪**：`03` 分支 3 `feat/strategy-greedy`。
**必带**：`engine/strategies.py` 全文 + `engine/models.py` 的类名。
```text
在 engine/strategies.py 里新增一个贪心策略，只改这一个文件。
要求：
1. 函数签名与 PLAN 一致：(req: PlanRequest, cfg: ScenarioConfig) -> PlanResponse
2. 必须复用 _fill_day / _build_days / _candidate_pool，不要自己重写铺时间轴
3. 排序键要有明确含义（例如 匹配度/在途分钟 的比值），注释里写清公式
4. 不许出现任何具体金额/标签/时间——阈值从 cfg 读，读不到就给中性默认（如 1.0）
5. 注册进 STRATEGIES，键名 "greedy"
6. 不要动 stub_plan / random_plan
```
**期望**：一个函数 + 一行注册 + 一段说明为什么这样排序。
**反模式**：说"写个更好的算法"——"更好"没有定义，它会抄 stub 换个排序键。

### T04 · 接入并跑评测

**用在哪**：T03 之后。
```text
新策略已注册为 greedy。现在：
1. 跑 .venv\Scripts\python.exe -m eval.baseline，把 greedy 那一行贴出来
2. 与 random、stub 逐列对比，指出 greedy 在哪几列更好、哪几列更差
3. 如果 greedy 总分低于 random，先不要改代码，先分析原因（打分口径？候选池？时间窗？）
```
**期望**：一张对比表 + 归因分析。
**反模式**：直接让它"把 greedy 调到比 random 高"——会变成对着指标过拟合。

### T05 · 修 bug 的标准话术（**用得最多**）

**用在哪**：任何"AI 改完但结果不对"的时候。
**必带**：出错文件全文 + 复现命令 + 真实输出 + 期望输出 + 一句"只允许改哪里"。
```text
现象：<一句话>。
复现：.venv\Scripts\python.exe main.py --request mock\case_tight.json
实际输出：<粘贴关键几行>
期望输出：<粘贴或描述>

请在 <文件路径> 内定位覆盖/错误点，只改这个文件。
不要改 engine/models.py、不要改 schemas/、不要新增依赖、不要改测试。
改完给我：
① 改动的 before/after（带行号）
② 为什么会这样（根因，不是"我调整了一下"）
③ 我该跑哪条命令验证
④ 会不会影响现有测试
```
**期望**：三段式 `Root cause / Patch / Verify`。
**反模式**：① 只说"预算不生效"不给复现命令 → 它会跑去改 `llm/parser.py`；② 贴整个仓库 → 它会顺手重构；③ 不说"只改哪个文件" → 它会去 `models.py` 加字段，触发契约变更。

### T06 · 写数据驱动测试

**用在哪**：换数据之后、修完 bug 之后。
```text
给 <模块> 写 unittest，要求：
1. 不许断言具体条数（如 len==8）和具体 ID（如 P001）——数据一换就会红
2. 必须保留硬约束：至少 1 条、ID 唯一、时间格式 ^\d{2}:\d{2}$、坐标在 -90~90 / -180~180
3. 数据边界（空矩阵、只有 1 条）用 self.skipTest，不要 fail
4. 用标准库 unittest，不许引入 pytest
5. 每个 test_ 函数写一句中文 docstring 说明"它在防什么"
```
**期望**：测试文件 + 一句"这几条为什么不会随数据变化而红"。
**反模式**："给这个模块写测试"——它会写 `assertEqual(len(pois), 8)` 这种脆断言。

### T07 · 代码审查（只读）

**用在哪**：合并前、答辩前。
```text
只读，不要改代码。以审查者身份读这几个文件：<路径列表>。
输出一张表：严重度(P0/P1/P2) | 文件:行号 | 问题 | 为什么是问题 | 建议改法。
P0 = 会让程序崩或结果错；P1 = 违反项目约定（分层、业务外置、契约冻结）；P2 = 可读性。
不要给"整体写得不错"这类评价。
```
**期望**：分级问题表。
**反模式**："帮我看看有没有问题"——会回一堆"建议加类型注解"。

### T08 · 小重构（行为不变）

**用在哪**：代码能跑但结构别扭时。
```text
重构 <文件> 的 <函数>，要求行为完全不变：
1. 先跑一次 43 个测试并记录结果
2. 只做结构改动，不改任何判断条件、阈值、返回类型
3. 改完再跑一次，必须仍然 43 个全绿
4. 用 main.py --request mock\case_basic.json 前后输出必须逐字相同
```
**期望**：改动 + 两次测试记录 + 输出比对。
**反模式**："顺便优化一下性能"——会顺手改算法。

### T09 · 加 UI 控件

**用在哪**：`03` 分支 5 `feat/ui-multiday`。
```text
在 ui/app.py 加 <控件>，要求：
1. 不许改 engine/、不许改 data/
2. 新控件必须加 key=，并在 on_change 里用 _mark_touched 记一笔
   （本项目的约定：默认跟随需求文本，用户手动动过才覆盖）
3. 切场景时要能被 _reset_inputs 清掉，记得把它加进清理清单
4. 展示逻辑放 ui/render.py，app.py 只留交互
```
**期望**：改动 + 说明"动过/没动过"两种情况下行为分别是什么。
**反模式**：不说覆盖语义 → 会写成无条件覆盖，把文本里的预算又抹掉。

### T10 · 解释报错

**用在哪**：看到红色 traceback。
```text
这段报错帮我定位，只解释不改代码：
<粘贴完整 traceback>
我执行的命令：<命令>
我的判断：<你猜的原因，可以错>
请回答：① 最后一行在说什么（人话）② 出错的直接原因和根本原因 ③ 最小修复方案（改哪个文件哪一行）④ 怎么验证修好了
```
**期望**：四问四答。
**反模式**：只贴最后一行 `KeyError: xxx`——上下文没了，AI 只能猜。

### T11 · 写报告"算法设计"章节

**用在哪**：`03` 分支 7。
```text
基于 engine/strategies.py 的 greedy_plan 写报告的"算法设计"一节，要求：
1. 先给问题形式化：决策变量、目标函数、约束（用公式）
2. 再给算法：伪代码 + 时间复杂度 + 空间复杂度
3. 最后给对照：从 eval/results.md 引具体数字，说明相对 random 的提升百分比
4. 不要写"本算法高效且鲁棒"这类空话，每一句都要有数字或公式支撑
5. 面向数学学院读者，可以出现求和符号、最优化记号
```
**期望**：公式 + 伪代码 + 带数字的对照。
**反模式**："帮我写算法章节"——会得到一篇"随着人工智能的发展"。

### T12 · 答辩讲稿与预设问答

**用在哪**：答辩前一周。
```text
基于项目现状写 3 分钟讲稿 + 10 个预设问答，要求：
1. 讲稿分四段：问题（30 秒）/ 做法（60 秒）/ 证据（60 秒）/ 不足（30 秒）
2. "证据"一段必须引用 eval/results.md 的具体数字
3. 预设问答要覆盖：为什么不用现成地图 API、算法复杂度能不能上规模、两人各自做了什么、AI 用了多少、数据从哪来、为什么这样打分
4. 每个回答不超过 4 句话，能用数字就用数字
```
**期望**：讲稿 + 问答表。
**反模式**：不给项目现状就让它写 —— 会写出与你实现不符的内容。

### T13 · 生成 commit message 与 PR 描述

**用在哪**：每次提交前。
```text
根据 git diff 生成：
1. 一条 Conventional Commits 格式的 commit message（中文），第一行不超过 50 字
2. 正文用短横线列 3~6 条，每条说清"改了什么 + 为什么"
3. 一段 PR 描述：改了什么 / 怎么验证 / 有什么风险
不要写"优化了一些细节"这种无法验证的话。
```
**期望**：可直接 `git commit -F` 的文本。
**反模式**：让它"随便写个 commit message"——会得到 "update files"。

### T14 · 让 AI 产出"只读验收清单"

**用在哪**：你不确定该验什么的时候。
```text
只读，不要改代码。针对本次改动，给我一份验收清单：
每条包含：编号 | 可执行命令（含完整 .venv\Scripts\python.exe 前缀）| 期望输出 | 不符合时的修法。
要求命令都是只读的（不许写文件、不许 git commit），并且要能在 Windows PowerShell 里直接跑。
```
**期望**：可复制的检查表。
**反模式**：让它"跑一遍测试"——它会说"测试通过"，而实际没跑（见 `01` 5.1 的说明）。

## 四、反模式清单（12 条）

| # | 坏提示词 | 为什么会跑偏 | 改法 |
|---|---|---|---|
| 1 | "帮我把这个项目优化一下" | 没有边界，它会改 5 个文件 | 一次只改一个函数，给完成标准 |
| 2 | "顺便把代码整理得更规范" | 顺手重构会破坏已通过的测试 | 规范问题另开一条分支（T08） |
| 3 | 只贴报错最后一行 | 没有上下文，只能猜 | 贴完整 traceback + 命令 |
| 4 | 一次要求改 5 个文件 | 出问题无法定位是哪一处 | 拆成 5 轮，每轮跑一次测试 |
| 5 | 不说验收标准 | 它认为"能跑"就是完成 | 写清"哪条命令、什么输出" |
| 6 | 让 AI 自己决定数据结构 | 会加字段，触发契约变更 | 明确"不许改 models.py" |
| 7 | "写个更好的算法" | "更好"无定义 | 给出排序依据与要对比的指标 |
| 8 | 不给复现命令 | 它会去改错误的层 | 现象 + 命令 + 实际/期望输出 |
| 9 | 让它"跑一下测试" | 它没法真的跑 | 你自己跑，让它给命令 |
| 10 | 说"随便你安排" | 它会引入新依赖或新目录 | 明确不许装新包 |
| 11 | 一个对话里从改代码聊到写报告 | 上下文污染，开始改结构 | 按 `05` D5 开新对话 |
| 12 | 让它"保证没问题" | 空头承诺 | 要它列出自查项并逐条回答（T15） |

## 五、提示词版本管理

- 卡片编号 **只增不改**。要改就新增 `T05-b`，并在旧卡上标"已被 T05-b 取代"。
- 每张卡用完后在末尾记一行：`上次使用：<分支> / <日期> / <效果>`
- 同一张卡连续两次效果不好 → 说明卡片本身有问题，改卡片而不是改措辞重试。
