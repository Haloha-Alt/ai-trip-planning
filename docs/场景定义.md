# 场景定义 · 日常出行规划

> 版本 v1.0 ／ 2026-10-28 ／ 本文件是**工程口径**的唯一场景来源。
> 课程口径（提交物、评分细则）在 `需求说明书.md`，两份互相引用、不复述。
> 数据落地看 `data/README.md`，参数落地看 `config/scenarios/*.toml`。

---

## 一、一句话

**人的一天怎么走，而不是游客的一天怎么玩。**

用户用一句自然语言说出"我要去哪、几点前必须到、路上顺便办什么、能花多少钱"，系统在硬约束下排出一条可执行的当日路线，并解释**每一站为什么是它、为什么是这个时刻**。

## 二、用户画像

| 项 | 内容 |
|---|---|
| 主要用户 | 在校大学生（本校本部，日常半径约 3 km 生活圈 + 偶尔进城） |
| 次要用户 | 教职工、校内工作人员 |
| 不服务 | 跨城旅游、长途自驾、团队包车（超出本项目范围，明确不做） |
| 城市定位 | **城市只是数据路由**（`data/cities/registry.toml`），不是业务前提。同一套逻辑换个城市包即可用，代码零改动 |

## 三、六种情形（每种的判定与指标）

| # | 情形 | 触发输入 | 关键约束 | 好坏的判断 |
|---|---|---|---|---|
| 1 | **赶课** | "八点前到教学楼，路上取个快递" | 到达截止时刻（`deadline`）+ 途经点顺序（`waypoints`） | 准点率：是否在截止前到达；超时即硬失败 |
| 2 | **办事链** | "取快递、打印、再吃饭" | 顺序敏感（`waypoints` 强制先后） | 顺序是否被遵守；是否漏办 |
| 3 | **时间紧** | "只有一个半小时" | 时间窗极窄，站数自动收缩 | 是否排满而不超时；是否有空转等待 |
| 4 | **预算紧** | "今天就 20 块" | 预算上限 | 是否零超支；同等满意度下是否更省 |
| 5 | **雨天** | 天气接口返回降雨 / 用户说"下雨了" | 室内优先，户外点降权或剔除 | 室内占比；重排后是否仍满足硬约束 |
| 6 | **多天** | "这三天分别安排" | 跨天不重复、每天独立时间窗 | 站点去重；每日可行性 |

## 四、硬约束（六类，违反即记为 warning，绝不抛异常）

1. **时间窗**：当日 `day_start` ～ `day_end`，且每站落在自身营业时段内
2. **到达截止**：`deadline` 之前必须抵达（对应违规码 `DEADLINE_MISS`）
3. **预算**：`daily_budget`（0 或空 = 不限制，不是"0 元"）
4. **营业 / 闭馆日**：`closed_weekdays` + 分时段营业（食堂早/中/晚三段各自成行）
5. **站点唯一**：同一 `poi_id` 一天不重复出现
6. **体力**：当日停留分钟数总和上限（由 `pace` × `max_poi_per_day` 决定，不在代码里写死）

## 五、优化目标与三档权重

沿用 `PlanMetrics` 四维（`satisfaction` / `cost` / `time` / `distance`）+ `feasibility` 扣分，**不新增指标**（保住 AC-31 与前序基线可比）。

| 档位 `profile` | 语义 | satisfaction | cost | time | distance |
|---|---|---|---|---|---|
| `save` | 省钱优先 | 0.30 | 0.50 | 0.15 | 0.05 |
| `fast` | 省时优先 | 0.30 | 0.15 | 0.45 | 0.10 |
| `comfort` | 舒适优先（少走路、多停留） | 0.45 | 0.20 | 0.20 | 0.15 |

权重写在场景 TOML 的 `[weight_presets.*]`；`PlanRequest.profile` 为空时用场景的 `[weights]`。**代码里不出现任何权重数字。**

## 六、可解释性要求

每一站必须能回答两个问题，缺一不可：
1. **为什么是它** —— 命中了哪个兴趣词 / 哪个标签 / 哪个途经点
2. **为什么这个时刻** —— 前序站的停留 + 在途时间推算，且落在营业时段内

输出的 `reason` 字段承担这件事；UI 与网页都要能直接展示，不允许只给"综合评分高"这种废话。

## 七、契约适配结论（重要）

现有 `PlanRequest` 覆盖约 80%（`city` / `days` / `start_time` / `end_time` / `daily_budget` / `interests` / `avoid` / `pace` / `mobility` / `date` / `travelers` / `budget_basis` / `top_n` / `seed`）。

缺三项，按**只增不改**补进 v1.3（全部带默认值，旧 JSON 不受影响）：

| 新字段 | 默认 | 谁消费 |
|---|---|---|
| `deadline: str` | `""` | `engine/constraints.py` → 违规码 `DEADLINE_MISS` |
| `waypoints: list[str]` | `[]` | `engine/strategies.py` → 起点之后强制顺序 |
| `profile: str` | `""` | `engine/planner.py` → 选 `[weight_presets]` |

## 八、已知缺口（如实记录，不粉饰）

| 缺口 | 现状 | 处置 |
|---|---|---|
| ~~`must_visit` 是死字段~~ | **2026-10-30 已接通**：必去点先落位（顺序不限），漏排报 `MUST_VISIT_MISS` | 见 `04` AC-61 |
| ~~`origin` 是死字段~~ | **2026-10-30 已接通**：按 `poi_id` / 名称匹配到 POI 时，第 1 天第一段在途从它算起 | 见 `04` AC-62 |
| ~~`closed_weekdays` 只在 `ctx` 路径生效~~ | **2026-10-30 已接通常规路径**：候选池按 `req.date` 的星期直接排除 | 见 `04` AC-60 |
| 距离为直线估算 | haversine × 速度，未走真实路网（大连仅 145 条步行实测边，北京 0 条） | 答辩口径写明"近似、不用于导航"；页面用 `meta.data.matrix_edges` 如实报覆盖度 |
| `close_time` 只做"跳过"不做"等待到开门再去" | 到站已过关门时刻的点直接不排，不会自动改到第二天 | 日常出行里"这家关门了就换一家"更合理，够用 |

## 九、六个可跑的自然语言例句（写文档就得能跑）

1. 「八点前到第一教学楼，路上帮我把快递取了」
2. 「下午先取快递，再打印，最后找个食堂吃饭」
3. 「我只有一个半小时，随便逛逛」
4. 「今天只有二十块，能去哪」
5. 「下雨了，帮我改成室内的」
6. 「这周六周日各安排一天，别重复」

## 十、明确不做

跨城交通、酒店与门票、真实导航路径、多人偏好协商、实时公交到站。范围越窄越容易做透。
