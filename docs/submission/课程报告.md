# AI 日常出行规划与行程调整助手 —— 课程报告

> 课程：《AI 大模型及其运用》· 项目 05「AI 出行规划与行程调整助手」
> 小组：2 人 ｜ 场景锁定：**日常出行**（不是游客一日游）
> 代码仓库：`https://github.com/Haloha-Alt/ai-trip-planning`
> 报告版本：v1.0 ／ 2026-10-30

---

## 摘要

我们做的是一个**日常出行规划器**：用户用一句自然语言说清"今天要干什么"，系统在硬约束
（时间窗、预算、开门时间、闭馆日、途经顺序）下排出一条可执行的行程，逐站给出理由，
并且可以导出、可以一句话局部调整。

与"景点一日游"类作品的三个区别：

1. **场景是真的日常**：数据是某高校生活圈的 46 个点（教学楼、图书馆、四个食堂、快递点、
   打印店、校医院、银行网点……），不是旅游景点列表；
2. **优化与评分同源**：贪心的目标函数用的就是评分函数的权重，不存在"算法觉得自己更好了、
   分数却更低"的两套口径；
3. **不确定性都摆在明面上**：哪些数据没核实、哪些在途时间是直线估算、哪些约束没满足，
   都由应用自己说出来（`meta.pending`、`meta.data.matrix_edges`、`warnings`），而不是藏在报告里。

评测结果：6 个用例 × 4 个策略，平均总分 `two_opt` 0.5835 > `greedy` 0.5819 > `stub` 0.5007
> `random` 0.4954，真算法比随机基线高 **17.8%**。测试 210 个全绿。

## 一、问题与用户

### 1.1 真实问题

学生一天的真实出行不是"去五个景点"，而是**一串必须做完的琐事**：

> 上午去图书馆自习，中午食堂吃饭，顺便取快递，别太赶。

这句话里有四类信息：目的地（图书馆、食堂、快递点）、先后偏好（顺便=顺路）、
软约束（别太赶 → 每天少排两站）、隐含硬约束（图书馆 07:30 才开门、食堂 19:30 关门、
快递点午休、周一博物馆闭馆）。

人手排这件事的成本不是"算不出来"，而是**算不完**：要同时记住 46 个点的开关门时间、
30 多个点对之间的步行耗时、预算和"别太赶"。排完之后一旦有人说"第 2 站太贵了"，
又要重排一遍。我们要解决的就是这个"重排成本"。

### 1.2 用户画像与六种情形

| 情形 | 典型输入 | 关键约束 |
|---|---|---|
| 上课日 | 八点前到教学楼，课间顺便打印 | 到达截止、硬顺序 |
| 自习日 | 上午图书馆自习，中午吃饭 | 开门时间、停留时长 |
| 办事日 | 取快递、打印、买文具、理发 | 多任务、预算 |
| 通勤日 | 从宿舍到教学楼，别绕 | 只求最短 |
| 雨天 | 下雨，全改室内 | 偏好切换（室内标签） |
| 赶时间 | 只有一个半小时，随便逛逛 | 时间窗极短、可空行程 |

六种情形对应 5 套场景配置（`daily` / `commute` / `errand` / `rainy` / `tight-budget`），
**换场景只换 TOML，代码零改动**。

## 二、需求分析

### 2.1 课程硬要求 → 我们的落点

| 课程要求 | 我们怎么落 |
|---|---|
| 自然语言输入 → Python 处理 → 结果展示 | 三个入口共用一份用例层：CLI、Streamlit、HTTP + 网页 |
| 费用要有**计价单位** | `POI.cost_unit`（人均/单次/每晚），界面上显示"人均 12 元" |
| 数据要记**来源与适用日期** | `POI.source` + `POI.source_date`；没填的进"待核实清单" |
| 必须区分**已核实 / 待确认** | `meta.pending` 逐条列出，网页与 Streamlit 都显示 |
| 演示必须做**两日行程** | 多天切段，地图分色，时间轴每天一条 |
| 演示必须做**闭馆 / 晚到**对照 | 关门就跳过（不再"排完再报错"）、闭馆日不进候选池、早到要等开门 |
| 应用要**主动提示**、不藏停用条件 | `warnings` + `meta.pending` + `meta.data`，四条降级链都留痕 |
| 保存恢复后结果一致 | 同输入同输出（固定种子、实时数据先抓快照再注入） |

### 2.2 评分口径（四维 + 总分）

`总分 = (0.45·满意度 + 0.25·预算友好 + 0.20·时间利用 + 0.10·路程紧凑) × 可行性`

- **满意度**：命中兴趣标签的比例（没填兴趣时退化为静态质量分）
- **预算友好**：`1 − 日均花费 / 日均预算`（多天先折日均，否则两天必判超支）
- **时间利用**：停留时长 / 可用时间窗
- **路程紧凑**：`1 − 在途 / (停留 + 在途)`
- **可行性**：每条违规扣 0.2（`BUDGET_OVER` / `TIME_WINDOW` / `CLOSED` / `DUPLICATE` /
  `NO_CANDIDATE` / `DEADLINE_MISS` / `WAYPOINT_MISS` / `MUST_VISIT_MISS`）

权重写在 `config/scenarios/daily.toml`，另有 `save / fast / comfort` 三档预设（`PlanRequest.profile`）。
**代码里不出现任何业务数值** —— 这是项目的硬规则（见 §3.4）。

## 三、系统设计

### 3.1 分层与调用链

```
入口层   main.py（CLI）   ui/app.py（Streamlit）   api/server.py + web/index.html（网页）
   ↓ 都只调用例层
用例层   service/usecases.py   options / build_request / plan_from_text / adjust_plan / save_plan
   ↓
引擎层   engine/planner.py（唯一入口 plan）
         ├─ strategies.py    策略注册表：stub / random / greedy / two_opt
         ├─ constraints.py   硬约束校验 + 四维评分
         ├─ adjust.py        局部调整（打补丁 → 重铺时间轴 → 重算分）
         └─ models.py        冻结契约（v1.4）
   ↓
数据层   data/loader.py（唯一出口）→ data/cities/<key>/*.csv（城市 = 数据路由）
```

三条纪律：

1. **`engine/models.py` 是冻结契约**：只允许末尾追加带默认值字段，不改不删；
2. **分层单向**：`ui → service → engine → data`，界面不许直接读 CSV；
3. **业务数值只准写在 TOML / CSV 里**，Python 里出现 `60` 元或 `4.5 km/h` 都算违规。

### 3.2 三条"换东西不改代码"的设计

| 想换什么 | 改哪里 | 代码改动 |
|---|---|---|
| 换算法 | `strategies.py` 写一个函数 + `STRATEGIES[name] = fn` | 0 行（其余代码只认注册表） |
| 换场景/城市 | `config/scenarios/*.toml` / `data/cities/registry.toml` | 0 行（城市是数据路由） |
| 换界面 | `web/` 或 `ui/`，只吃 `service` 的输出 | engine 不动 |

### 3.3 契约与并行

`PlanRequest`（22 字段）/ `PlanResponse`（9 个顶层键）冻结在 `engine/models.py`，
`schemas/itinerary.schema.json` 是它的机器可读版本，`tests/test_golden.py` 把
**键集合**、**黄金行程**、**评分基线**三件事钉死。

结果：两个人可以并行改"算法"和"界面"，因为接口不变；改字段必须同步三处
（models / schema / docs/接口契约），并被 AC-02 卡住。

### 3.4 "不写业务数值"是怎么落实的

- 预算、时间窗、节奏系数、交通速度、权重、默认站数 → `daily.toml`
- POI 的坐标、开关门、停留、花费、标签、闭馆日 → `data/*.csv`
- 代码里只剩"读配置、比大小、算加权"，`docs/04` AC-03 用 grep 卡这条规则

## 四、关键实现

### 4.1 算法：从"最想去的"到"此刻最划算的"

| 策略 | 一句话 | 用途 |
|---|---|---|
| `stub` | 按兴趣匹配度排序后顺序铺时间轴 | 默认策略，基线 |
| `random` | 固定种子随机挑点随机排序 | **故意做笨的对照组** |
| `greedy` | 每步在"装得下"的候选里挑净收益最高的一站 | 真算法 |
| `two_opt` | 贪心选点 + 2-opt 改序（硬顺序前缀不翻转） | 真算法（略优） |

贪心的净收益：

```
u = w_sat·满意度 + w_time·(停留/可用时长) − w_cost·(花费/剩余预算) − w_time·((在途+干等)/可用时长)
```

四个细节值得说：

1. **只在可行解里挑**：超预算、装不进时间窗、会在关门前走不完的候选，根本不进比较；
2. **干等也扣分**：06:30 出门却排一个 07:30 才开门的点，等于白等一小时；
3. **目标函数与评分同源**：优化的就是评的，避免"算法更好、分数更低"的两套口径；
4. **预算极紧时降级**：放开预算重排一次，超支由约束层如实报 —— 宁可给不完美结果，
   也不给"今天没地方去"的空行程。

评测（`eval/results.md`，`--scenario daily`，6 用例 × 4 策略平均总分）：

| 策略 | 平均总分 | 相对随机基线 |
|---|---|---|
| `two_opt` | **0.5835** | +17.8% |
| `greedy` | 0.5819 | +17.5% |
| `stub` | 0.5007 | +1.1% |
| `random` | 0.4954 | — |

如实记两个反例：`case_basic`（8 条占位数据的黄金样例）上 `stub` 0.8309 > 真算法 0.8204；
`case_empty`（兴趣全不命中、满意度全 0）上随机基线偶然更高。原因写在 `docs/04` AC-49。

### 4.2 时间轴：三段而不是两段

一条行程段其实有三种状态：**在途**、**等开门**、**停留**。
早期版本只用"在途 + 停留"，于是 `arrive = max(路上到的时间, 开门时间)` 一取 max，
"等开门"就被画成了"在路上走了很久"，整段右移。

现在按"上一站离开 → 在途 → 等待 → 停留"四时刻拆开，等待段单独用橙色，
图例里写明「等开门」。这类错误纯文本断言抓不到，我们用无头浏览器截图核对。

### 4.3 解说与局部调整（AI 部分怎么用）

- **解说** `llm/narrate.py`：有 Key 用模型（过长度与字段校验），没 Key 用规则模板 ——
  **永远有结果**，断网不会白屏。
- **局部调整** `llm/adjust.py`（听懂）+ `engine/adjust.py`（改对）：
  解析成 `drop / replace / add / swap` 补丁，**只动被点名的那一站**，改完重铺时间轴、重算分数。
- **连续调整**：`/api/adjust` 接受 `instructions: [...]` 按顺序重放。
  早期版本每次从原始行程重放，第二次会把第一次吞掉（提示却写"已调整"）—— 这是真实修过的 bug。

### 4.4 降级链：任何一环坏掉都不许崩

| 坏在哪 | 怎么降级 |
|---|---|
| 城市未注册 | 打印一次 warn，回退默认数据 |
| 城市没有交通矩阵 | **不借用别的城市的边**，全部直线估算，`meta.data.matrix_edges = 0` 上屏 |
| CSV 编码不对 | utf-8-sig → gbk 回退，坏行跳过 |
| 天气/实时接口失败 | 返回"没有实时数据"，不重排也不报错 |
| 大模型不可用 | 规则模板解说 |
| 候选被过滤光 | 放宽到全部 POI（宁给不完美结果，不给空行程） |
| 预算极紧 | 放开预算重排 + `BUDGET_OVER` 如实报 |

## 五、数据

- **大连凌水生活圈 46 个点**：教学楼 4、图书馆 3、食堂 5、快递/打印/超市/理发等生活服务 12、
  运动场馆 4、交通节点 3、校外 4、其他 11；每个点带坐标、开关门、建议停留、花费与计价单位、标签、质量分。
- **145 条高德步行真实耗时**（`tools/amap_matrix.py` 生成，运行期零联网）：
  覆盖 46 点 1035 个点对的 **14%**，其余由 haversine × 时速估算。
  公共交通/驾车的实际在途时间**全部是直线估算**（高德公交接口对个人 Key 不开放，返回 10002）。
- **诚实性口径**：全部 `source = seed`、`source_date` 留空、坐标为校区近似值；
  应用把用到的点列进 `meta.pending`，界面上写"待核实（N 项）"。
  **没有编造任何未核实的开放时间与价格** —— 宁可写"待确认"，也不写一个看起来很真的数字。

## 七、局限与改进方向

如实列出，不粉饰：

1. **在途时间是估算**：只有 145 条步行实测边，公交/驾车全为直线估算；
   矩阵覆盖 14%，跨校区行程的时间会偏乐观或偏悲观。
2. **`two_opt` 相对 `greedy` 增益很小**（0.5835 vs 0.5819），6 个用例里有 4 个分数完全相同 ——
   数据规模太小，局部搜索没多少可优化空间。
3. **`close_time` 只做"跳过"，不会"等到明天"**；跨天重排目前仍是"每天独立排"。
4. **真实路网/瓦片地图未接入**：地图是离线 SVG 等距投影，只表示相对位置与先后顺序。
5. **北京这类的第二城市只有 12 个点、0 条路网**，只用于验证"换城市不改代码"，不用于实际出行。
6. **解说的语言质量依赖模型**；没 Key 时是模板句，够用但不动人。

改进优先级（如果还有一周）：接公交/骑行真实耗时 → 跨天统一优化（把整趟当一个大 TSP）
→ 用户画像与历史偏好 → 真实瓦片地图。

## 八、分工与协作机制

| 角色 | 负责 |
|---|---|
| 甲 | 引擎与数据：`engine/*`、`data/*`、`eval/*`、契约与评测 |
| 乙 | 交互与呈现：`web/*`、`ui/*`、`service/dto.py`、报告与答辩 |

共同文件（`models.py`、契约文档、`config/scenarios/*.toml`）改动前必须知会；
`main` 上任何时候跑 `unittest` 必须全绿。

协作机制里最有用的三件事：

1. **验收清单当合同**：64 条 AC，每条都是"跑什么命令、期望什么输出、不符合怎么修"，
   AI 交活后 5 分钟就能判收不收。
2. **冻结契约**：字段只增不改，两个人的并行不会互相踩。
3. **把结论落盘**：每个决定写进 `docs/`，避免换个对话就改回去（这个项目里真的发生过 3 次）。

## 九、结论

这套系统做到了：**一句自然语言 → 一条守住硬约束、逐站有理由、随时能局部改的行程**，
并且在数据不完整、网络不可用、大模型不可用的条件下都能给出结果，同时把"哪些不确定"
明确告诉用户。

技术上最值得说的不是算法多复杂（贪心 + 2-opt 都是教科书方法），而是
**把"可解释、可降级、可验收"做成了结构性约束**：契约冻结、数值外置、验收清单、
降级链、诚实的待核实清单。这些约束让一个两人小组在课程周期内能持续交付而不返工。
