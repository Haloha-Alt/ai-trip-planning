## 1. 问题（1.5 min）

> "我们的题目不是'帮我安排一次大连一日游'，而是**今天这一天怎么过**。"

念一句真实输入：

> 上午去图书馆自习，中午食堂吃饭，顺便取快递，别太赶。

拆给评委看：这句话里其实有四类信息 —— 目的地（图书馆、食堂、快递点）、
先后偏好（顺便 = 顺路）、软约束（别太赶 = 每天少两站）、隐含硬约束
（图书馆 07:30 才开、快递点午休、周一博物馆闭馆）。

"人排这个不是算不出来，是**算不完**：46 个点的开关门、30 多个点对的步速、
预算、还有'别太赶'。而且只要有人说一句'第 2 站太贵了'，就得重排。
我们做的就是把这个重排成本降到一句话。"

## 2. 现场演示（5 min，三条主线）

### 准备

```bat
cd /d D:\projects\ai-trip-planner
.venv\Scripts\python.exe -m api.server
```

浏览器开 `http://127.0.0.1:8000/`。**什么都不要改**，先确认两个下拉框是
「场景 daily / 算法 stub」—— 如果显示 greedy 或 commute，说明配置被改坏了（见 §7）。

### 主线 A：一句自然语言 → 一条行程（90 s）

1. 文本框保持默认：「上午去图书馆自习，中午食堂吃饭，顺便取快递，别太赶」
2. 点「生成行程」

说三件事：

- 指标卡：满意度 / 预算友好 / 时间利用 / 路程紧凑 / 可行性 / 总分；
- 行程表：每站有理由（"命中兴趣：自习、图书馆"、"到早了等开门 30 分钟"）；
- 顶部三行小字：**实时天气**（有就报，没有就说为什么）、**实测路网 N 条边**、
  **待核实 N 项** —— 这三行是"不装懂"的证据。

### 主线 B：两日 + 闭馆/晚到对照（120 s）

1. 天数改 `2`、每天站点数改 `3`，点「生成行程」→ 切到「地图」页签：
   两天两种颜色、虚线连线、圆点里是**当天**序号、站名不叠。
2. 切「时间轴」页签：每天一条横条，蓝色停留 / 灰色在途 / **橙色等开门**，
   刻度是真实整点，空白处就是真的空闲。
3. 把出发时间改成 `06:20` 再生成 → 第一站前面出现**橙色等待段**，悬停显示"等开门 N 分钟"。
4. 把出发时间改成 `17:00`、返回 `17:30` → 页面显示
   「这一天的行程是空的 —— 通常是时间窗太短」，**不崩**，并给 `NO_CANDIDATE` 提示。
5. 补一句"关门"的对照（命令行更快）：

```bat
.venv\Scripts\python.exe -c "from engine.models import PlanRequest; from engine.planner import plan; r=plan(PlanRequest(city='dalian', top_n=4, start_time='16:50', end_time='21:30', interests=['看病','邮政']), scenario='daily', strategy='stub'); print([(i.name,i.arrive,i.leave) for d in r.days for i in d.items]); print(r.warnings)"
```

念结论：17:00 关门的校医院**不会被排进去**，也不会出现"排完再报 CLOSED"这种自相矛盾的输出。

### 主线 C：算法对比 + 一句话调整（90 s）

1. 点「算法对比」→ 结论句 + 表格（最优行 ★ 绿底）+ 条形图（以本次最高分为满格）。
   念：`two_opt` 比随机基线高约 18%；**如实说明** 6 个用例里有 4 个 two_opt 与 greedy 同分
   （数据规模小，局部搜索没多少可优化空间）。
2. 回「行程表」，在「一句话调整」里输入 `第2站太贵了换一个` → 应用 →
   只有第 2 站变了，其余顺序内容不变，指标与总分**当场重算**。
3. 再输入 `删掉第1站` → 应用 → **第一次的调整还在**（第二次不会把第一次吞掉）。

### 兜底（如果现场没网/服务起不来）

```bat
.venv\Scripts\python.exe main.py --request mock\case_multiday.json
```

命令行输出同样是完整行程 + 提示，可以照着讲。

## 3. 设计取舍（4 min）

只讲三个"为什么这样而不那样"，每个都带一个能被追问的证据：

1. **为什么冻结契约**：两个人并行改算法和界面，靠的是 `PlanResponse` 不变。
   证据：`engine/models.py` 只允许末尾追加字段，`tests/test_golden.py` 把键集合钉死，
   `docs/04` AC-02 用 `git diff` 卡"有没有删字段"。
2. **为什么业务数值全外置**：预算 60 元、步速 4.5 km/h、权重 0.45/0.25/0.2/0.1 都在
   `daily.toml`。现场可以**直接改一个数值再点生成**，证明"换场景不碰代码"。
3. **为什么优化和评分用同一套权重**：否则会出现"算法觉得更优、分数更低"的荒唐局面；
   贪心的目标函数就是评分函数（`_weights()` 与 `constraints.score()` 同源）。

如果要讲算法本身：

- 贪心：每步在"装得下"的候选里挑净收益最高（满意度、停留正收益，花钱、在途、**干等**负收益）；
- 2-opt：贪心选点后改序，**硬顺序前缀（起点/途经点/必去点）不翻转**；
- 降级：预算极紧时放开预算重排一次 + 如实报 `BUDGET_OVER`——宁可给不完美结果，不给空行程。

## 4. 结果与诚实性（2.5 min）

投 `eval/results.md` 的表（6 用例 × 4 策略）：

| 策略 | 平均总分 | 相对随机基线 |
|---|---|---|
| two_opt | 0.5835 | +17.8% |
| greedy | 0.5819 | +17.5% |
| stub | 0.5007 | +1.1% |
| random | 0.4954 | — |

然后**主动说局限**（这一段是加分项，不是减分项）：

1. 在途时间只有 145 条步行实测边（覆盖 14%），公交/驾车**全是直线估算**；
   所以页面会显示"实测路网 145 条边"或"该城市暂无实测路网"。
2. `two_opt` 与 `greedy` 在多数用例上同分，增益有限。
3. 46 个点的开关门与价格是**种子数据**、坐标是校园近似值，
   用到的点会进"待核实清单"——**我们没编造任何未核实的数字**。
4. 数字必须能复现：同输入同输出，`eval.baseline` 跑两次逐字节一致。

## 6. 可能被问到的问题

| 问题 | 怎么答 |
|---|---|
| 这不就是 TSP 吗？ | 不是。这里有时间窗、开门时间、预算、硬顺序，是带时间窗与预算约束的定向问题（OP/TOP 变种）；而且我们的目标不是"最短"，是"四维加权最划算"。 |
| 为什么不精确求解？ | 46 点的小规模下 DP 也能跑，但状态含时间与预算，维数爆炸；课程周期内优先把"可解释 + 可降级"做扎实。2-opt 是性价比最高的改进。 |
| 数据是真的吗？ | 坐标与开关门是校区近似值，明确标注"待核实"，并在界面上列出来；只有步行耗时是真实 API 取的（145 条），公交接口个人 Key 不开放。 |
| 大模型用在哪？ | 解析（规则优先 + 模型兜底）、解说、局部调整的意图理解。**没有 Key 也完全可用**（规则模板），这是设计要求：永远有结果。 |
| 误差多大？ | 步行有实测的点对误差接近 0；没有的点对是直线 × 4.5 km/h，校园内一般偏乐观 10–30%。跨校区行程误差更大。 |
| 两个人怎么并行？ | 冻结契约 + 验收清单 + 分层单向；`main` 上任何时候测试必须全绿。 |
