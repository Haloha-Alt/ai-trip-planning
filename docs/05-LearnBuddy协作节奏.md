# 05 · LearnBuddy 协作节奏

> 版本 v1.0 ／ 2026-10-27 ／ 本文件只谈"对话怎么管"，不谈代码。
> 提示词正文在 `02`，操作步骤在 `03`。

---

## 一、为什么要管对话

### 1.1 三个真实成本

| 成本 | 具体表现 |
|---|---|
| **上下文污染** | 一个对话里先改 UI、再聊报告，AI 会把"写文档"的语气带进代码，开始加注释块、改函数名 |
| **返工累积** | 同一个对话里连续三次改法都被推翻，第四次它还在沿用前三次的错误假设 |
| **结论丢失** | 聊了很久定下的结论（"预算 0 表示不限制"），换个对话就忘了，于是又改回去 |

### 1.2 一个真实的反例

> 你在同一个对话里：先让它修 `ui/app.py` 的预算覆盖问题 → 然后问"帮我想想报告怎么写" → 然后说"顺便把 `strategies.py` 也优化一下"。
>
> 结果：它把"优化"理解成重构，动了 `_fill_day`，`random` 基线跟着变了，`eval/results.md` 全变。
> 你回头查不出是哪一步坏的 —— 因为三件事缠在一条时间线上。

## 二、开新对话：6 条硬判定（任一命中就开新的）

> 都是**可观察的条件**，不是"感觉聊乱了"。

| 编号 | 条件 | 30 秒怎么核对 |
|---|---|---|
| **D1** | 你接下来要改的**顶层目录**，与本对话已经改过的不同 | 往上翻，看 AI 改过的路径前缀（`ui/` / `engine/` / `data/` / `docs/`） |
| **D2** | 同一个现象你已描述 **≥2 次**，且每次它的改法都被你 `git restore` 撤销了 | 数一下对话里出现了几次"还是不对" |
| **D3** | 你已经在这个对话里贴了 **≥3 个文件**的完整内容 | 数代码块个数 |
| **D4** | `git branch --show-current` 的结果，与本对话开场时说的分支**不一样** | 跑一条命令 |
| **D5** | 本轮产出物的类型变了：`.py` → `.md` / `.pptx` / 讲稿 | 一句话就能判断 |
| **D6** | AI 出现了"忘记规则"的信号：提议改 `engine/models.py`、提议装 `pytest`、提议"顺手重构一下无关文件" | 看它上一段话 |

### 2.1 判定自检卡（30 秒填完）

```
[ ] D1 我要改的目录变了？          是 → 开新
[ ] D2 同一问题第 2 次返工？        是 → 开新
[ ] D3 本对话已贴 3 个以上文件？    是 → 开新
[ ] D4 分支变了？                  是 → 开新
[ ] D5 产出物类型变了？            是 → 开新
[ ] D6 AI 提议越界操作？           是 → 开新
```

## 三、继续当前对话：3 条判定

| 编号 | 条件 | 例子 |
|---|---|---|
| **C1** | 同一个 bug 的第二次尝试，且这次只改一个文件 | "改成用 `on_change` 回调记账试试" |
| **C2** | 只是补充信息 | 贴一段新报错、贴新的命令输出 |
| **C3** | 只差"验证结果"这一步 | "跑通了，43 个测试全绿" |

**C1 的边界**：第 3 次尝试就触发 D2，必须开新对话。

## 四、新对话开场模板（可复制）

### 4.1 模板

```text
【身份】你是我的 Python 项目协作助手。先只读，不要改文件。
【项目】<粘贴 02 文档 1.4 的固定上下文包>
【仓库】D:\projects\ai-trip-planner，远程 origin 已接通
【分支】<git branch --show-current 的真实输出>
【目标】<这次只做一件事，一句话，可验收>
【硬规则】
  1. 不许改 engine/models.py / schemas/itinerary.schema.json / docs/接口契约.md
  2. 不许新增依赖
  3. 不许整文件重写，只给带行号的局部替换
  4. 业务数值只能写进 config/scenarios/*.toml 或 data/*.csv
【已知上下文】<上一轮结论 / 已经试过并失败的方案>
【验收标准】<哪条命令、什么输出算完成>
先回：① 你对任务的理解 ② 打算改哪些文件 ③ 你看到的风险。等我确认再动手。
```

### 4.2 每段为什么要写

| 段 | 不写会怎样 |
|---|---|
| 身份 | 它会直接开始改代码，而你想先对齐理解 |
| 项目 + 固定上下文包 | 它不知道分层和契约，会往 `models.py` 加字段 |
| 分支 | 它给你的命令可能基于错的分支，`git diff` 全乱 |
| 目标（一句话） | 范围失控，一次改 5 个文件 |
| 硬规则 | 顺手重构、顺手装包 |
| 已知上下文 | 重复提已被否决的方案 |
| 验收标准 | 它认为"能跑"就是完成 |

### 4.3 填好的实例

```text
【身份】你是我的 Python 项目协作助手。先只读，不要改文件。
【项目】（粘贴固定上下文包）
【分支】fix/dead-links
【目标】让侧边栏参数只在"用户手动改过"时才覆盖解析结果
【硬规则】1. 不改 models.py/schemas/契约 2. 不加依赖 3. 只改 ui/app.py
【已知上下文】当前是无条件覆盖，导致文本写"预算 100"被默认值 0 抹成不限制
【验收标准】不动控件时 daily_budget=100.0；手动设 200 时为 200；设 0 时为 null
```

## 五、一条分支的对话节奏（四步）

| 步 | 目的 | 用哪张卡 | 产出 |
|---|---|---|---|
| 1 开工对话 | 对齐理解，不改代码 | `T00` 或 `T01` | 三段回复（理解 / 文件清单 / 风险） |
| 2 实现对话 | 真正改代码 | `T03` / `T05` / `T09` | 补丁 + 根因 + 验证命令 |
| 3 验收对话 | 确认没破坏别的东西 | `T14` 或直接自己跑 `04` | 通过 / 不通过清单 |
| 4 收尾对话 | 出提交信息 | `T13` + `T15` | commit message + PR 描述 |

### 5.1 一条分支应该开几个对话

| 分支 | 预期对话数 | 说明 |
|---|---|---|
| `fix/dead-links` | 3~4 | 一处 bug 一个对话，或按文件合并 |
| `feat/data-real` | 2 | 数据整备 1 个 + 验收 1 个 |
| `feat/strategy-greedy` | 2~3 | 算法 1 个 + 评测 1 个 |
| `feat/ui-multiday` | 2 | 控件 1 个 + 展示 1 个 |
| `docs/submission` | 2~3 | 报告 1 个 + 讲稿 1 个 |

**超过预期对话数 = 说明任务本身该拆得更细，不是对话开多了。**

## 六、对话内的话术（四句，各有用）

| 场景 | 说什么 |
|---|---|
| 让它先别动手 | **"先不要改文件，只给方案，等我确认。"** |
| 它跑偏了 | **"你改了不该改的 `<文件>`，撤销这部分，只保留 `<文件>` 的改动。"** |
| 要求自查 | **"列出你这次改动的所有文件与行数，并逐条对照我给的硬规则。"** |
| 要可执行结论 | **"给我一条能直接复制到 PyCharm Terminal 的命令，带完整 `.venv\Scripts\python.exe` 前缀。"** |

**万能兜底**：当它给的答案让你不确定是否真的验证过，问一句 ——
> "这条命令你自己跑过吗？把真实输出贴给我。没跑过就说没跑。"

## 七、把对话结论固化回仓库

对话会丢，仓库不会。**每次对话结束前，至少留下一样东西**：

| 落盘位置 | 写什么 |
|---|---|
| commit message 正文 | 改了什么 + 为什么（3~6 条） |
| `docs/需求说明书.md` | 助教答复的原始内容（Q1–Q13） |
| `docs/04-验收清单.md` | 新发现的验收项（加 AC 编号） |
| `docs/02-提示词手册.md` | 新踩的坑 → 补进反模式清单 |
| `docs/00-总纲与路线图.md` | 决策与取舍（"为什么不用 Folium"这类） |

### 7.1 三行决策记录（推荐格式）

```markdown
- 2026-10-27 · 决定：预算 0 表示"不限制"而不是"0 元"
  原因：UI 上"0"最容易被当成未填写；内部用 None 表达"不限制"
  影响：config 里 daily_budget=0 会被 load_scenario 转成 None
```

### 7.2 什么必须落盘

1. 改过的**字段语义**（否则下次又改回去）
2. **没采用的方案**及原因（否则会被反复提议）
3. **踩过的坑**（进 `02` 反模式清单或 `01` 故障速查）

## 八、常见误用（5 条）

| 误用 | 后果 | 正确做法 |
|---|---|---|
| 一个对话干到底 | 上下文污染，越改越乱 | 按 D1–D6 切 |
| 每句话开一个新对话 | 每次都要重贴上下文，效率极低 | 按 C1–C3 判断可继续 |
| 贴整个仓库 | 噪声大、AI 抓不住重点 | 只贴要改的文件 + 相关测试 + 报错原文 |
| 不说分支名 | 它给的命令基于错分支 | 开场就写 `git branch --show-current` |
| 让 AI 决定"要不要升契约版本" | 它会顺手升，两个人都要跟着改 | 契约变更只能人决定，见 `接口契约.md` 三条纪律 |
